# PhiAgent 项目工作空间设计草案

这份设计将 PhiAgent 从持续对话扩展为可持续推进的项目。用户已明确第一版需要兼具研究写作、研讨辩论和现实项目孵化；三者是同一个工作空间中的工作方式，可以往返切换。每个项目保存问题、材料、论证、讨论、任务、行动与成果，用户离开后能继续推进，也能查看判断和方案为何发生变化。本文是设计方案，不表示相关功能已实现或上线。

需求依据来自用户提出的三种并存的工作需要，以及现有代码的会话、原典、文件和记忆能力。尚未开展真实用户访谈；下面的用户分层和使用障碍属于待验证的产品假设。哲学研究已有可以借鉴的文献工具和研究助手，不能据此宣称这是无人做过的领域。

## 用户需求与第一版范围

| 用户及场景假设 | 用户实际想完成的工作 | 当前聊天形态的不足 | 工作空间应提供的结果 |
| --- | --- | --- | --- |
| 哲学学生和认真读者 | 读懂一部原典，留下自己的问题与理解 | 解释分散在聊天里，重开对话后难以接续阅读 | 阅读位置、批注、概念辨析和能回到原文的研读记录 |
| 论文与专题研究者 | 缩小问题，组织资料，形成并修订一个论证 | 答案多而论证状态不清，原文与解释难以对应 | 研究简报、证据关联、最强异议、可编辑且有版本的文稿 |
| 教师和研讨组织者 | 让多人围绕共同问题讨论，并保留真正的分歧 | 对话记录不能说明谁主张什么、回应了哪一个异议 | 议题、真人与模拟角色身份、共享材料、分歧及后续问题 |
| 公共议题和实践项目参与者 | 从事实、价值和利益冲突走到可试验的行动 | 模拟讨论与现实材料容易混淆，方案缺少反馈入口 | 调查材料、方案、行动记录、评价条件与复盘；不以模拟预测冒充现实结果 |

第一版同时覆盖认真研读者、研究写作者、研讨组织者和实践发起人，以能将一个问题持续推进的人为共同用户。休闲提问继续使用现有自由对话，不强迫所有用户创建项目。项目可从研究、研讨或实践开始，也可混合使用；共享同一套资料、讨论、文稿与版本机制，不建立三份孤立数据。

### 需要先验证的假设

1. 用户最常丢失的是研究状态、依据与修订理由，而非聊天本身。
2. 文稿和材料同时可见，比单纯长聊天更利于推进有成果要求的工作。
3. 不同阶段需要不同工作对象：原文与文稿、议题与交锋、行动与反馈；统一界面需要允许切换关注对象。
4. 历史哲学家人格带来不同的判断视角，但不能替代材料真实性和论证检验。
5. 用户愿意选择性地将讨论保存为研究对象，而不愿逐轮填写大量结构化字段。

可先招募研读者、论文写作者和研讨组织者各几位做形成性访谈，不把小样本当作市场规模或效果证明。请用户展示最近一次真实研究：材料在哪里、最后一次修改为什么发生、重新开始时要花多久恢复状态。再用同一材料完成一个短任务，观察能否定位依据、回应异议和修改自己的文稿。

## 项目需要持续保存什么

项目以一个正在被研究的问题为中心，不以某个哲学家或单次聊天为中心。人物可以参与多个项目，同一项目也可有不同讨论与工作任务。

| 研究对象 | 保存内容 | 必须保留的区分 |
| --- | --- | --- |
| 项目简报 | 核心问题、范围、暂定假设、预期成果、约束和下一步 | 假设不是已证实结论；目标允许修订 |
| 资料 | 原始文件或原典引用、作者、版本、取得范围、来源与定位 | 原典、译注、二级研究、经验材料和模拟发言分别标明 |
| 研读记录 | 阅读位置、批注、概念说明、疑问、原文片段 | 用户解释、模型解释与原文不能混在一起 |
| 论证记录 | 主张、理由、前提、异议、回应、适用范围和材料关联 | 材料支持事实或作者归属，不自动证明规范主张正确 |
| 讨论 | 消息、回答者身份、参与职责、所引用对象及当时版本 | 模拟角色立场不自动成为用户立场；讨论过不等于认同 |
| 工作任务 | 本轮目标、工作对象、运行状态、完成条件、结果和续接点 | 任务完成不代表研究争点已经解决 |
| 行动与反馈 | 行动问题、假设、执行人、时间、观察标准、实际记录及材料 | 待试方案、模拟推演、真人反馈和观察事实分别保存 |
| 文稿与成果 | 可编辑正文、引用、修订建议、版本和导出文件 | 草稿、待采纳意见和用户认可的判断分别保存 |

这些对象按需产生。用户可以直接写一段文稿或继续聊天，再把有用的片段保存为论证、问题或批注，无须一开始填完一个数据库。

## 核心使用过程

### 开始项目

创建时只要求一个问题或项目标题。可选研究、研讨、实践或混合工作方式；预期成果与资料导入均可选，默认私人项目、默认项目主持为深哲。允许从零开始，也允许把一篇文章、一部原典或一段既有对话作为起点。

深哲协助澄清范围，但不要求用户先拥有完整论文提纲。项目简报应短：我们在问什么，目前怎样理解它，哪些材料最相关，下一步准备做什么。用户可直接修改，后续调整保留版本。

### 研读并积累材料

从平台原典、上传文件或实际取得的公开文献建立项目资料条目。保留原始文件或稳定引用，抽取文本仅作为一个可阅读版本；页码、字符位置与版本信息分别处理。

选中一个原文片段，可以向深哲或某位哲学家提问、做自己的批注、保存疑问或关联到现有主张。默认只围绕选中对象及其必要上下文工作，不将项目全部文件无差别塞进每次请求。

### 让讨论进入研究

讨论可以随意展开。用户有需要时，再将一段发言保存为待检验主张、异议或问题。保存动作同时带上发言者、来源、当前文稿位置和对象版本；模型提出的整理也可作为待采纳候选。

例如研究“同情是否赋予行动道德价值”，康德可从自己的义务与自律立场回应；另一位参与者提出异议。系统保留这些是模拟角色发言，待作者借原典和论证检验以后，才能将某个解释写成文稿中的作者归属。

### 写作和修订

用户与 agent 围绕同一个可编辑文稿工作。选中段落后，可请求解释、追问、反驳、改写或核对出处。默认展示本次工作的对象和取用资料，修改建议可以逐段采纳、调整或舍弃。

用户自己编辑时自动保存；授权 agent 编辑草稿时也可以直接形成新版本，不要求每个常规操作再次批准。涉及用户已认可的研究判断时，提出可见的修订意见和理由，保留原版本，不悄悄把聊天中的新立场覆盖为正式结论。修订审阅是研究交接方式，不是所有动作的许可弹窗。

### 离开后继续

重新进入项目，用户先看到当前问题、上次工作的文稿、尚未解决的异议和续接点。继续按钮应指向具体任务，例如“补查这段引文的语境”，而不是仅重发“继续”。未解决的分歧可以长期存在。

### 研讨与真实辩论

项目可以创建一场围绕具体争点的研讨。真人成员可以发表立场、提供材料、回应指定发言；哲学家模拟角色以自身人格参与，不混同真人或原典作者的历史发言。发言记录保留其所回应的主张，主持人可以将分歧整理到争点列表。

第一版支持邀请项目成员、异步讨论、手动推进回合和导入实际会议记录。实时共同编辑、音视频会议和复杂会议调度可以后置，但不能将“几个模型互相说话”当作已经支持真实辩论。对话可以结束于未解决的分歧、共识条件或需要补查的事实，不靠投票裁定哲学正确性。

### 现实项目孵化

从现实问题开始，保留实际条件和参与者，再将价值分歧转成可比较的方案与可以观察的行动。记录行动对象、负责人、时间、希望观察什么、哪些情况会改变判断，以及实际得到的反馈。执行可以由真人在现实中完成，再把记录带回项目。

例如围绕 AI 写作责任，可以研究作者责任，组织真人与模拟角色的研讨，再试办写作工作坊，收集参与者实际记录，修订原先方案。模拟只能提示假设与可能的冲突，不冒充实际访谈、执行结果或预测验证。第一版提供方案、行动记录与反馈复盘；不要求首发就让 agent 自动替用户执行现实事务。

## 信息架构与界面

### 全局导航

左侧保留自由对话，新增项目列表；智能体广场、原典库和设置是全局入口。历史会话可以移入一个项目，也可以继续独立存在。项目与人物不构成双重归属：人物回答归属于消息，讨论归属于项目。

### 项目导航

推荐项目内保留总览、资料、讨论和成果四个共用入口，另以研究、研讨、实践切换当前工作方式。研究打开原文、论证和文稿；研讨打开议题、发言及分歧；实践打开方案、行动及反馈。工作记录与任务状态在有关对象旁显示，不再增加一个庞大的仪表盘。对象可以打开为工作标签，减少反复离开上下文。

推荐桌面布局为左侧项目与对象导航、中间当前材料或文稿、右侧研究伙伴与相关讨论。阅读和写作优先时，工作对象占主要空间；纯讨论时，讨论可以扩展为中心。移动端一次展示一个主要区域，通过明确的项目和对象入口切换。

提供两种可讨论的布局方案：

- 工作对象优先：中间是持续编辑的文稿、议题记录或行动计划，右侧讨论绑定当前对象。适合材料与成果同时推进，是推荐的默认布局。
- 问题与活动优先：中央先展示当前主张、交锋或行动状态，选择一项后打开其讨论及成果。适合研讨主持和实践推进，可作为另一项目视图。

两种视图都提供三种工作方式，并使用同一项目对象，不能形成两份互不相通的数据。初版论证以列表和关联记录实现，复杂自由图谱编辑可以后置。

### 界面状态

必须能区分空项目、正在读取资料、正文尚不可读、材料读取失败、任务运行中、用户停止、草稿冲突、建议待采纳、对象更新后待复核和已归档。来源检索失败不能表现为已经读过或该研究不存在。

进展用具体状态表示，例如“版本待确定”“这个异议尚未回应”“草稿已修订”。不显示真理完成度、不用 agent 投票或虚构分数证明结论可靠。

## 哲学家人格如何进入工作空间

每位参与者有两个独立维度：是谁，以及正在承担什么工作。康德的身份由他的 soul 与原典维持；批评文稿是这一次的职责。不能把所有人都改造成语气相同的研究助理，也不能用项目共同指令覆盖各自的哲学前提。

深哲可承担研究主持、综合整理与工具调度。哲学家按自己的立场解释、追问、论辩或起草，保留发言身份及其与用户观点的区别。项目简报和相关材料作为工作上下文进入，而非新的人格体系。来源没有取得时，角色仍可讨论，但不能将模拟判断充作已查证引文。

当前测试哲学家只有原典发现与读取工具。第一版可将其意见保存为项目候选，由已获授权的项目编辑机制处理写入；未来添加机械性的项目读写工具，也不必添加额外人格库。专业文献综述、经验资料搜集和实际调查职责应由具备相应工具的研究主持或研究角色承担，不能通过改一个名字假装具备能力。

多角色任务应明确要检验的主张、可共享的材料及各自职责。默认不自动召集所有人物；建议从少数有明确分歧的参与者开始。不同角色使用同一基础模型的交锋能帮助提出异议，却不构成独立验证，也不以多数赞成宣布真理。

## 持续上下文与版本

需要分别管理账户背景、项目上下文、讨论历史和单次任务上下文。跨项目只默认共享用户明确保存的个人资料与交流偏好；其他项目的材料、观点、私密讨论和未采纳结论不会自动混入。用户显式引用另一个项目时，保留引用关系与原有权限。

项目持续上下文保存经用户认可的简报、当前文稿版本、关键来源、尚未解决的异议与续接点。模型自动摘要保留为可修订记录，不能将“讨论过某理论”改写成“用户相信某理论”。引用角色观点时保留角色身份。

每次修改关联对象原版本。并发编辑遇到版本不一致，展示差异或重新生成建议，不能静默覆盖。来源的正文或版本改变后，受其影响的引用和论证记录标为待复核，不自动撤销用户观点，也不继续显示旧核验状态。

初版提供文稿与方案版本、项目快照和明确成员权限。讨论与正式成果可供获授权成员使用，个人未共享笔记和受限资料保留其范围。后续可分出不同解释或行动方案进行比较，类似隔离工作的版本分支，但无需让哲学用户管理 Git 分支。

## 研究 agent 的执行能力

工作任务应有目标、对象、完成条件和可见运行状态。状态可包括待运行、运行中、等待用户信息、已暂停、已完成、部分完成、失败和已取消。任务结果关联实际读取的资料、产生的文稿版本及尚未完成的部分。

用户可以在任务进行时继续编辑或打开另一讨论；输出仍回到原任务和原对象，不能写入当前恰好显示的项目。后台运行应有任务队列、取消与恢复机制和用户可设的资源范围，不默认无限续跑。自动监测、定时工作与外部发布留到用户明确启用时。

短任务的完成条件是完成所求工作。复杂研究任务可以通过有依据的答复、明确保留的异议或已形成且可检查的草稿完成；不强迫价值分歧收敛为唯一答案。正式成果发布与现实行动另有明确的用户动作，不能从研究讨论自动推断授权。

## 与现有项目的衔接

已确认的基础包括：会话级持久化和版本冲突处理、账户背景与记忆、流式任务所有权、文件转文本、平台原典阅读、研究来源存储、121 个回答入口。当前缺少项目归属、长期资料对象、共享文稿版本、论证关系和项目级任务续接。这些判断来自下列现有代码，而非假设已有完整 workspace。

建议增加项目与成员、项目资料、对象关联、文稿及版本、任务、行动反馈和变更事件。将现有 conversation 以可空的 project_id 接入：未归项目的历史会话保持原行为，迁移不重写回答者。同步时需在前端归一化和后端索引返回中同时保留项目归属。

建议新增项目 API 与界面，继续使用 PhiAgent 现有账户、后端和静态构建路径。保留 `/agent` 与 `/agent/c/:conversationId`，另加项目入口，例如 `/agent/p/:projectId`；不改现有组件名称或旧路由。

项目私有文件和用户文稿不能写入 `app/public/`，也不能改写 `backend/data/book_chapters/`。原典只通过现有 ID、版本、位置及内容指纹引用。原始私人资料与其抽取版本放在受账户权限约束的工作空间存储，项目索引与现有研究衍生库分开。云端或本地托管的具体方案需根据持久化和多人需求另行确认，不能把现有上传转文本直接当作已经持久保存原文件。

### 推荐先实现的数据对象

| 对象 | 关键字段与关系 |
| --- | --- |
| Project | 所有者、标题、问题、简报、工作方式、状态、修订号 |
| Membership | 项目与真人成员、主持/编辑/评论/阅读权限；邀请及接受状态 |
| Conversation | 可空项目归属；保留现有消息及逐条回答者身份 |
| Source | 项目归属、来源类型、作者和版本、原始对象、访问状态、读取范围及位置 |
| Artifact | 项目归属、类型、正文、当前版本；类型可为文稿、研读记录、论证或方案 |
| Relation | 来源、主张、异议、段落和讨论间的明确关联；关系由作者或候选整理产生 |
| Revision | 原对象版本、改动、提交者、产生任务、时间与修订理由 |
| Run | 项目、讨论与目标对象、目标、状态、完成条件、结果及续接点 |
| Action and Feedback | 项目、行动目标、负责人、时间、观察标准、实际记录、材料与状态 |

## 建设顺序与验收

| 阶段 | 建设范围 | 应能检查的结果 |
| --- | --- | --- |
| 第一版 | 共用项目与简报、已有聊天归入、持久资料、文稿和方案版本、论证与异议列表、真人成员和异步研讨、行动计划与反馈、项目上下文隔离 | 研究、研讨、实践都能实际进行，彼此共享依据与成果，退出后准确恢复 |
| 第二版 | 原文并排对照、复杂论证视图、少量角色协作、实时编辑、可续接的后台研究任务 | 能追溯观点依据、比较修订和不同角色贡献，任务中断后仍可继续 |
| 第三版 | 音视频会议与会议集成、方案分支、外部工具执行、用户启用的定期跟进 | 实际执行与反馈更易进入原项目，仍保留角色、来源和权限边界 |

第一版需要三个都能跑通的验收过程：研究用户加入材料、展开不同角色讨论并修订同一文稿；研讨用户邀请真人、回应具体发言并保留未解决分歧；实践用户保存方案、执行一项现实行动并录入反馈，依据反馈修改方案。三者可以发生在同一项目中。退出重开后，问题、资料位置、文稿、角色、版本、行动和下一步均保留。另验收以下边界：

- 项目 A 的私人材料不会进入项目 B 的请求；角色发言不会变为用户的信念。
- 切换项目时，运行中的任务仍写回原项目和原对象。
- 文稿同时被用户修改时，旧建议不会覆盖新版本。
- 未读来源、读取失败和来源版本变化保持可见。
- 正式引文能回到实际材料的相应位置；导出也保留必要出处。
- 原有自由对话、尼采与哲学家人格、阅读器和历史路由继续可用。

成功指标应基于真实工作：恢复研究状态所花时间，定位依据是否成功，用户是否能自己重建并修改论证，建议实际被采纳或拒绝的原因，产生的成果是否继续使用。聊天条数、角色数量和停留时间只能辅助观察。

## 借鉴依据与仍待决定的问题

Codex 的长期工作强调持久项目状态、可检查的产出和用户持续纠偏，这能借鉴到研究任务和文稿版本。[OpenAI 官方说明](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)。Zotero 将阅读、批注、笔记和来源返回联系起来，可借鉴材料与研读记录的关系。[Zotero 阅读与笔记文档](https://www.zotero.org/support/pdf_reader)。Obsidian 的 Bases 展示如何让已有笔记及其属性形成多种视图，可借鉴研究对象的不同工作视角。[Obsidian Bases 文档](https://obsidian.md/help/bases)。这里的哲学项目对象与建设优先级是本方案的设计判断，不是这些工具现有功能的直接复述。

本地依据：`docs/ui/information-architecture.md`、`agent-app/src/data/conversationLogic.js`、`agent-app/src/data/conversationStore.js`、`backend/account_data.py`、`backend/account_context_messages.py`、`backend/routes/agent_history.py`、`backend/routes/upload.py`、`backend/routes/research.py` 与 `docs/agent/academic-roadmap.md`。
